## What the required suites prove

- exact literal public commands, wrong-stage/surface rejection, state-bound expiry/stale behavior, challenge use, and single-use approvals;
- schema/version/config consistency and Python syntax without generated bytecode;
- implicit Phase compatibility, explicit multi-Phase contract rules, dependency-cycle rejection, repair default/range, stale-state fencing, broad create/modify/delete mutation accounting, reasoning-only Diagnosis/Recovery, and stale-manifest failure;
- normal two-Phase execution with immutable Work binding, persisted read-context grant, generation fencing, unauthorized mutation rejection, fresh Repair Attempt, Task Gates, Phase Gates, and final Evaluation routing;
- escalated Diagnosis -> reasoning-only Recovery -> Recovery Contract -> fresh Recovery Ticket/Builder -> immutable Recovery Contract binding -> normal Task Gate -> issue resolution -> Phase Gate;
- deterministic release-manifest coverage with cache/runtime exclusions.

## Known limitations

- The candidate is validated as a filesystem working copy rather than a new Git commit, so it has no candidate commit SHA.
- Semantic architecture correctness remains a reasoning responsibility; deterministic gates verify declared bindings/evidence/executable checks rather than pretending to infer architecture semantics.
- v5.2 in-flight execution is intentionally not auto-upgraded; migration fails closed and requires a quiescent/replanned boundary as documented in `MIGRATION_V5_2_TO_V5_3.md`.
