# Workplan v5.3.0 — Deterministic Phase/Task/Attempt Control Plane

`Workplan/` is the durable authority layer for Project Template. v5.3 strengthens execution proof while preserving a small public UX.

## Public UX

Normal users use exact commands only:

```text
EXECUTE_RESEARCH       # External AI
EXECUTE_PLANNING       # External AI
EXECUTE_IMPLEMENTATION # VS Code / ExecutionManager
WORKPLAN_NEXT          # either surface; authoritative continuation
WORKPLAN_STATUS        # read-only status
```

Reset commands are explicit and approval-gated. See `ENTRY_PROMPT.md` for the complete token list and surface rules.

## Runtime hierarchy

`Cycle -> Phase -> Task -> Attempt`

- A Task belongs to exactly one Phase.
- If `Workplan/plan/PHASES.json` is absent, Tasks map deterministically to implicit `PHASE_001`.
- If `PHASES.json` exists, Tasks must declare `phase_id`.
- Phase and Task dependency graphs are validated and must be acyclic.
- `max_repairs` defaults to 2 and may be configured from 0 through 5.

Planning publishes an immutable package digest covering the implementation plan, Phase authority, Task index/contracts, and compiled architecture/interface artifacts. Material post-`PLAN_READY` edits invalidate execution authority.

## Work and Attempt identity

Every Builder dispatch creates a fresh Attempt (`INITIAL`, `REPAIR`, or `RECOVERY`) and a durable ticket. Attempt identity binds Cycle, Phase, Task, Work, generation, Scope digest, Planning Package digest, Phase digest, Task digest, and Recovery Contract digest when applicable.

On resume Workplan recalculates current bindings and compares them to the issue-time binding. A mismatch blocks; original bindings are never overwritten. Resume increments generation, fencing older sessions.

## Tickets

Builder tickets carry only bounded authority:

- current Cycle/Phase/Task/Attempt/Work/generation;
- immutable digests;
- authorized production paths;
- granted read context;
- declared verification/evidence requirements;
- kind-specific Repair or Recovery metadata.

Context grants persist across resume. They never expand `authorized_paths`.

## Production mutation authority

Builder Work records a full production snapshot before implementation and a mutation manifest on completion. Create/modify/delete changes are calculated first, then checked against the ticket authorization.

Control-plane paths under `Workplan/` are separate from production authority. `.git`, generated bytecode, common caches, virtual environments, editor-local directories, and temp files are excluded from production mutation accounting.

## Task Gate

Only deterministic Task Gate logic marks a Task PASS. It verifies at least:

- current Task/Phase/Attempt/generation;
- completed Builder Work;
- valid current ticket and digest;
- immutable Scope/Plan/Phase/Task/Recovery binding;
- unchanged approved Planning Package;
- structured evidence bound to current Attempt/ticket;
- declared verification exit codes;
- required evidence artifacts/digests;
- mutation-manifest identity;
- all production mutations within ticket authority.

## Phase Gate

A Phase cannot pass until all its Tasks PASS. Declared phase-level verification/evidence must pass, dependencies must already be satisfied, and no unresolved issue may affect the Phase. Only Phase Gate PASS allows the next Phase to become eligible.

## Repair and escalation

Local repair is bounded. Every repair gets a fresh Attempt and Repair Ticket bound to the parent failed Attempt. The default budget is 2; `0..5` is valid.

Execution escalates immediately when failure is structural (for example stale/invalid binding, ticket identity, contract/package integrity, or another authority defect) rather than consuming routine repairs.

## Diagnosis and Recovery

External Diagnosis and Recovery are reasoning-only Work. Production mutation during either role is blocked at Work completion.

Recovery produces a JSON Recovery Contract bound to an issue and Task. Recovery path authority may narrow but cannot silently expand the immutable Task authorization. Registering the contract returns the Task to deterministic execution; a fresh Recovery Builder Attempt is issued. The recovered implementation passes the same Task/Phase gates as any other implementation. The related issue is resolved only after Task Gate PASS.

## Approval

Approval challenges are:

- explicit human actions;
- time-bound;
- exact state/action/subject-bound;
- rotated after a wrong challenge;
- single-use.

Any intervening state transition makes an unconsumed grant unusable. AI cannot approve itself.

## Resume/reconciliation

`WORKPLAN_NEXT` and `Workplan/scripts/resume.py` reconstruct continuation from repository state. Reconciliation reports production-worktree changes relative to the active Work baseline. Chat history is never required for authority reconstruction.

## Validation

Generate the deterministic release manifest only after release files are stable:

```bash
python Workplan/scripts/integrity.py generate
```

Then run:

```bash
python Workplan/scripts/validate.py --full
```

Required suites cover exact commands, contracts/bindings/state/mutation/integrity, normal Phase/Task flow, and Diagnosis/Recovery flow. A skipped or timed-out required suite is a validation failure.

## Files with distinct ownership

- `Objective_dev.md` — development constitution.
- `ENTRY_PROMPT.md` — universal exact-command bootstrap.
- `control/STATE.json` — authoritative durable runtime state.
- `plan/` + `tasks/` + `compiled/` — Planning Package authority.
- `work/` — Work maps, checkpoints, tickets, evidence.
- `scripts/_core/` — deterministic authority mechanisms.
- `external_agent/` — bounded role constitutions, not workflow authority.
- `MIGRATION_V5_2_TO_V5_3.md` — explicit upgrade rules.
- `RELEASE_VALIDATION.md` — actual candidate verification record.
